# Using astack

## Discover capabilities

`astack --skill` prints this installed guide as Markdown with skill frontmatter. Invoke it without a subcommand. Use `astack --help` and command-specific `--help` for argument syntax. Help and command JSON remain available separately.

From the astack source repository use `pnpm dev` instead of `astack`; after building use `pnpm start`. An installed binary resolves this guide independently of cwd.

## Focused roles and user setup

`astack skills show orchestrator`, `astack skills show implementer` and `astack skills show reviewer` print narrower SKILL.md guides. Workers consume an explicit assignment and return proposals; the orchestrator chooses host follow-ups. Installation never grants worker publication/cleanup authority or changes saved runtime prompts.

`astack skills list --json` shows packaged versions/digests. `astack skills inspect --json` reports availability without creating files. Explicit `astack skills install --json` installs all three at `$CODEX_HOME/skills` or `~/.codex/skills`; select `--root <directory>` for another user/profile skills root and repeat `--role <orchestrator|implementer|reviewer>` to select roles. The root must exist or have a trusted existing immediate parent. Authored, edited, deleted-owned, foreign and pending targets are preserved; there is no force/adopt option. Versions/digests and owners are recorded through managed-file metadata. The global `--skill` still prints this command guide; role filtering uses `--role`.

A blocked installation can preserve existing files; pending means publication may have partially completed. Inspect the exact root/role and retain its journal rather than deleting claims or retrying by age. No agent settings/project files are rewritten, and repository context is not needed. Project initialization and automatic role binding remain later operations. See the packaged role guides for assignment-specific instructions; source contributors can consult `docs/skills.md` for installation/recovery contracts.

Global `--state-directory <path>` selects isolated host state. `--git-executable <absolute-path>` selects trusted Git; otherwise the CLI searches absolute host PATH entries. Git inspection requires Git 2.45 or later.

Context selectors are `--project <project-id>`, `--checkout <checkout-id>`, `--run <attempt-id>`, and `--path <path>`.

## Select the intended target

- From a neutral directory or another project, use an explicit project ID, checkout ID, or path. `project list` supplies saved IDs; listed paths are recorded facts and can be stale.
- Without selectors, context inspects the nearest Git repository from caller cwd. A collection directory never causes child-project discovery or guessing.
- An explicit project selects its primary checkout unless an explicit path selects another checkout belonging to that project. An explicit checkout selects that checkout.
- A saved attempt binds its project/repository/checkout. Other explicit selectors must agree. `--run` uses an existing persisted attempt ID; implementation/review submission creates durable runs. Saved assignment commits and observed HEAD are separate facts.
- Explicit targets override ambient cwd. An explicit `--path` is an assertion and must agree with other explicit selectors. Conflicts reject rather than falling back.

Context can inspect an unregistered repository without registering it or creating state. Register only when the user intends to establish a local project identity. Registration creates no project config, skills, worktrees, or execution policy. A linked checkout needs deliberate registration; it then shares project identity while keeping its own checkout ID. Independent clones and duplicate basenames remain separate.

Moved/replaced registrations reject as stale. Do not bypass this by silently selecting another checkout, changing IDs, or treating matching remotes as ownership. Relocation/reconciliation is not implemented yet.

## Interpret results

Read commands emit `{ schemaVersion: 1, outcome: 'completed', value: ... }` or `rejected` with a stable error code. Registration emits `persisted` with `disposition` and identities, `rejected`, or `uncertain`. A completed read is an observation; persisted registration is local identity evidence. Neither means an agent job was accepted.

After `uncertain`, inspect the registry and supplied identities before retrying persistence. No provider effect or automatic retry is implied. Missing state permits empty-registry diagnostics; unsafe/corrupt/incompatible state remains an error. Read-only commands do not migrate old schemas; deliberate registration or an explicit library read-write open can migrate them.

Doctor reports Git readiness, other providers as `not_checked`, configuration provenance as `none`/`not_checked`, and delegation as unavailable. Use `config inspect` for separate configuration evidence. Do not interpret registration or a clean checkout as execution authorization.

## Owned worktrees

Preparation requires a registered project, stable owner key, new task branch, and full local commit SHA. Optional `--checkout` selects a registered source and `--run` binds an existing saved attempt; branch/base must match that assignment. Existing branches are not adopted. Managed checkouts live in private containers under host state, and receive separate registered checkout IDs. Repeated prepare verifies/reuses the same resource; a pending reservation never launches a second writer.

Worktree outcomes include `prepared`, `reused`, `removed`, `reconciled`, `inspected`, `blocked`, and `pending`. Inspecting a pending record does not establish readiness. Routine removal preserves dirty, untracked, and ignored files, edited ownership markers, changed identities/branches, locked resources, and task branches. Attempt-bound cleanup also requires a terminal result and release of other retained resources. Host/runtime callers must independently establish that workers/services stopped.

After interruption, inspect the record and exact operation ID. Use `--writer-stopped` only after the trusted host/operator has verified the original writer and its children stopped. The flag is an attestation, not an automatic process check. Never infer it from PID absence, age, agent idleness, or a worker/PR assertion. Reconcile reads provider/filesystem evidence and settles state without repeating Git creation/removal. Unmarked containers and branch-only partial creation remain preserved; no force, branch deletion, or automatic repair is available.

Worktree creation currently rejects configured content-filter commands and sparse checkout until execution profiles support them. Project provisioning, LFS/submodule initialization and hooks remain later capabilities; runtime launch is separate from worktree preparation. Do not bypass a blocked/pending outcome by choosing a different directory or forcing Git cleanup.

## Approved project and role configuration

Use `astack config inspect --project <id> [--checkout <id>] [--role implementer] [--json]` (alias `config check`). It reads existing state and reports effective settings, leaf provenance, pinned skill versions/digests, and actionable prerequisites. Exit 1 means blocked or rejected; readiness launches no command and grants no durable execution capability.

Portable `.astack/project.json` is a proposal. The trusted host/operator maintains `<state-directory>/config/<project-id>.json` outside repositories with private directory/file permissions. Registration does not create or approve it. Do not copy a worker/PR proposal into this file as an automatic repair. Review and approval belong to the host/operator; there is no approval/init command yet.

Settings resolve defaults → user → approved project → local → request. Objects merge by fields; arrays replace completely. Host-only permissions, timeout limits and mandatory hooks apply after merging. A changed proposal blocks until reviewed; it never grants new permissions. Missing executables, approved environment names or exact protected skill bytes require the reported host action. Never put credential values in JSON, command arguments, skill contents or reports.

Library configured job acceptance saves immutable policy/provenance and skill pins. Its dispatch gate refreshes policy and prerequisites and blocks changed policy or legacy jobs without snapshots. Generic service dispatch is available through injected runtimes. Hook execution remains unavailable. Interactive agent launch requires the explicit codex-herdr service opt-in and supported role configuration. Do not bypass a block by removing a required hook, editing permission controls, or accepting a new job without host authorization.

## Local service and durable queue

Run `astack service run [--codex-herdr] [--capacity <count>] [--role-capacity <count>]` in the foreground with explicit host state. Use `service status --json` for live readiness/counts and `service inspect <job-id> --json` for saved job/attempt/effect evidence, including offline. `service wake` requests reconciliation after a meaningful external change; it does not clear unknown claims or grant permissions.

`service submit --project <id> [--checkout <id>] --role <name> --key <stable-key> --branch <branch> --commit <full-sha> --task '<description>' --json` persists generic delegation intent. Prepare/select the intended registered checkout explicitly. Submission creates no worktree. A receipt is durable intent, not agent start. Retry a lost acknowledgment with the same key; changed assignment/task/policy under that key conflicts. Never submit replacement work with a new key merely because the client disconnected.

The built-in `codex-herdr` runtime is enabled only with `service run --codex-herdr [--codex-executable <approved-absolute-path>]`. Configured executables alone do not register a runtime. This host opt-in accepts the configured local servers’ shell, inherited environment, canonical Codex resolution and ambient native configuration. Each project role still needs an unchanged enabled host policy selecting this runtime and approved command. Do not enable execution or substitute a worker merely to bypass a block.

One coordinator owns each private state directory through a kernel-backed lock. Other instances reject. SIGINT/SIGTERM drain foreground work and release the coordinator; they do not prove existing workers stopped. On restart, claimed launches are inspected without replaying them. Unknown launches retain capacity despite claim expiry. Only trusted runtime evidence can establish launch absence or quiescence. `awaiting_result` means a known worker stopped, not that the task succeeded.

Transport is a private Unix socket with same-host-user authority, not a TCP service or restricted worker-report endpoint. Use a short private state path if socket length is rejected. Preserve edited/unowned endpoint files and obtain host inspection; do not remove sockets, steal locks or force cleanup as an automatic repair. Runtime events, submissions, startup and explicit wake drive reconciliation; there is no recurring GitHub polling loop.

## Herdr project and worker layouts

Use `herdr configure --project <id> [--session default] [--socket <path>] [--label <text>]` to save an explicit host target without contacting Herdr. The shared default session is deliberate; use a named session only for an explicit isolation preference. `herdr ensure --project <id>` associates or creates one primary space without focus changes. `herdr inspect --project <id>` reads current evidence. Global `--herdr-executable <absolute-path>` selects trusted CLI code. Only installed protocol 22 is supported initially.

`herdr worker prepare --attempt <id>` opens an existing Astack-owned ready worktree in its saved project's primary group. It requires a saved attempt, valid accepted policy, exact initial branch/SHA, intact ownership and fresh registry identity. It creates no Git checkout and starts no agent. Existing unowned worker layouts block. The runtime consumes the saved expected agent name/pane.

`herdr worker inspect --attempt <id>` verifies current layout/attribution. `herdr worker bind-agent --attempt <id> --kind <kind>` records only an already detected matching agent, including actual foreground cwd, terminal and available native session ID. It launches nothing. Provider idle/done status is not task success or permission for another writer.

Targets always come from saved project settings, never caller cwd, `HERDR_*` pane variables or UI focus. Labels are presentation. A changed endpoint, moved pane, wrong cwd, replacement terminal/session or missing worker layout blocks; do not redirect old IDs or create replacement agents. Primary project spaces remain open, and worker resources are retained for later cleanup.

After an uncertain write, inspect its space/operation IDs. `herdr reconcile <id> --operation <id> --writer-stopped` only settles fresh matching evidence after trusted host confirmation that the original writer/children stopped and no late write can arrive. Never infer that from a timeout or idle agent. Reconciliation never repeats creation/opening; absent or changed evidence remains blocked. There is no force, close-group, automatic adoption, Herdr update, or fallback runtime repair.

## Interactive Codex controls

`runtime capabilities` prints supported controls without contacting state/providers. `runtime inspect --attempt <id> [--json]` reads saved intent and fresh identity. `runtime reconcile --attempt <id>` can bind a fully matching pending launch without repeating it. Launch happens through the capacity-owning service. Generic sessions receive no task prompt; the implementation workflow now supplies deterministic initial input.

Herdr owns execution. The host-approved command executable must match the selected canonical Codex path resolved by that server. Native arguments must include each flag once: `--sandbox read-only|workspace-write`, `--ask-for-approval on-request|never`, `--no-daemon`, `--no-alt-screen`. The adapter adds the fixed per-invocation override `-c check_for_update_on_startup=false` to avoid blocking worker startup on update menus, then appends the verified checkout with `--cd`. Manage Codex upgrades separately on the host; global/project configuration is unchanged and arbitrary config overrides remain unsupported. Other flags, hooks, requested environment/skills and control timeouts below five seconds report missing capabilities. Never drop required configuration to make a blocked launch pass. No headless, model routing, resume or bypass execution is supported.

`runtime input --attempt <id> --key <stable-key> [--codex-executable <approved-path>] [--json]` reads at most 16 KiB of UTF-8 from stdin; it accepts idle/done sessions and rejects approval dialogs, active/unknown UI and terminal control characters. Input is not echoed or saved; only its digest/key/acknowledgement are persisted. Herdr receives text in process argv, so do not include credentials. `runtime interrupt --attempt <id> --key <stable-key> ...` requests Escape; it does not establish cancellation or stopped descendants. Approval/question UIs require deliberate operator handling.

Each new control refreshes accepted policy and verifies saved project/checkout ownership, branch, endpoint, workspace/pane/terminal, foreground cwd and unique attempt name/kind. Input/interrupt target that name. Native session IDs are optional at binding; a captured ID must remain present and unchanged. Metadata first appearing later does not change a binding established without an ID. Missing/changed required evidence blocks; no fallback or replacement agent is launched. One trusted controller per worker and no reuse of reserved names are host preconditions: Herdr cannot atomically compare worker identity with a write or prove server executable resolution.

Repeated keys return the saved receipt/current observation; changed text/kind conflicts. A pending launch is never launched again. A pending input/interrupt blocks subsequent controls because UI state cannot prove delivery. Reconcile does not clear unknown delivery or absent launches; do not edit state, change keys, or start another worker to bypass uncertainty. Abort/timeout/service exit do not prove Herdr or Codex stopped. Idle/done and Escape acknowledge neither an accepted task result nor free capacity; explicit run operations handle report acceptance and cancellation separately.

## Explicit implementation delegation

Prepare/select a ready owned checkout first using the worktree primitives. Run the approved service/runtime and use `implement submit --project <id> --checkout <owned-checkout-id> --key <stable-key> --branch <branch> --commit <full-initial-sha> --task '<selected task>' [--criterion '<criterion>'] [--json]`. Criteria are repeatable. The role is fixed to implementer. A primary/unowned checkout is rejected. No implicit worktree, issue selection, setup, publication, PR or review is performed.

Acceptance saves task/criteria, instruction references, approved policy, job/attempt and pending effect before launch. Repeating the same normalized submission returns its original identity and saved state, including after worker edits or policy revocation; it grants no new execution authority. Changed intent under that key conflicts. A disconnected client must retry the same key, not create another worker. Scope project/checkout explicitly from any cwd.

Default instruction references are `AGENTS.md` and `AGENTS.override.md` under the assigned checkout. Repeat `--instruction <relative-Markdown-path>` to replace the defaults with an explicit list; include defaults yourself when adding more paths. Reads capture digests/absence without copying file contents or executing instructions. Symlinks, traversal, hard links, invalid UTF-8 and oversized files block. The worker must read applicable repository/directory instructions itself. Task/repository text does not grant host permission.

A read-only workflow preflight blocks changed ownership/branch/SHA/cleanliness/instructions before capacity claim or launch. Required configuration must remain approved. A runtime without declared implementation support reports `workflow_unavailable`; failed context preflight reports `workflow_blocked`. Fix the reported prerequisite deliberately and use `service wake` for a fresh pass. Do not remove required hooks/skills or substitute another checkout to bypass blockers.

Initial delivery includes saved IDs, checkout/root, branch/base SHA, task/criteria, instruction references and final JSON proposal contract. It uses `implementation:initial:v1` scoped to the attempt. Restart may deliver the first prompt only when receipt absence and fresh context are established. Acknowledged/pending input is never resent; changed bytes under its key conflict. Do not use the reserved key for manual runtime input. Generic `service submit` remains session-only; use `implement submit` for implementation handoff.

`implement inspect <job-id> --json` reads the last durable coordinator evidence, including offline. It distinguishes queued, starting, started, needs_decision, blocked, failed, unknown and awaiting_result. Inspection does not query live providers; wake the service after meaningful external changes. CLI exit 1 can describe an already accepted job's blocker/uncertainty, so preserve its identity and inspect instead of treating it as absent.

The worker returns a final JSON proposal with schema version, job/attempt/project/checkout, branch/base/current HEAD, `completed | needs_decision | failed`, summary and blockers. No report file needs to be committed. Explicit host report acceptance validates saved assignment and fresh evidence through `run report`; remote worker authentication and automatic transcript harvesting are not implemented. `acceptedOutcome` stays null until a terminal result is accepted. Idle/done, prompt acknowledgement or a worker's completed proposal never establishes accepted success, safe cleanup or released capacity. Handle approval/questions intentionally; never infer that interruption stopped all writers.

## Planned capabilities

The stage remains `foundation`. Initialization, automatic handoffs/report harvesting, runtime wake-up, review-result publication, and automatic checkout provisioning are not implemented commands. Report missing capabilities rather than inventing commands or treating unknown commands as accepted work.

As those operations arrive, use commit-specific results and explicit automation policy. A pushed PR or idle agent alone is not proof of completion or authorization for another action.

## Manually delegate PR review

Use `astack review submit --project <id> --checkout <dedicated-owned-checkout-id> --key <request-key> --branch <review-branch> --commit <full-pr-head-sha> --host github.com --repo <owner/repo> --pr <number> [--check <name>] [--json]` after explicit worktree preparation. The commit must already exist locally. No implementation job is required. Use the base repository/PR for fork PRs. Use a separate approved reviewer role; Codex static review requires `--sandbox read-only` in its trusted command. Static review starts no services.

Review is manual; submitting the command authorizes that exact request. It never discovers unrelated PRs or automatically starts after implementation. The service checks GitHub head/check evidence at acceptance and before dispatch/input. A stale head blocks; never silently submit a newer SHA. With no selected checks, all observed checks must pass and at least one must exist by default. `--check` is repeatable; each selected name must exist and pass. Missing/skipped/cancelled checks do not pass. This is not GitHub branch-protection evaluation.

GitHub readiness reads paginate check runs and commit statuses at the exact SHA, bracketed by unchanged PR observations. Page/deadline limits and ambiguous check names block. The optional targeted CI observer below requires explicit service opt-in and source enrollment. Separate library publication primitives and explicit implementation `handoff finish` exist; automatic publication hooks and review-result publication commands do not. Never treat an accepted report as GitHub write authorization.

`--override-gate <reason>` permits early CI review only when the private host policy sets `execution.review.allowGateOverride: true`. Record the pending/failing evidence; never invent success or use an override to bypass identity, ownership, host policy, capacity or resource requirements. `--resource <name>` records an integration resource request and blocks until isolated provisioning is implemented. `--instruction` replaces the default AGENTS Markdown paths.

A new key for the same project/repository/PR/SHA reuses the saved review and original checkout; aliases preserve retry identity. Different gate/resource/instruction/configuration requests conflict. `--repeat` requires a new key and fresh dedicated checkout and explicitly creates a new job/attempt. Reusing an implementation checkout or another review attempt's checkout is rejected. Active/needs_decision/cancel_requested reviews remain unresolved; targeting a terminal review with a new key requires explicit repeat.

Use `astack review inspect <job-id> [--json]` for saved target, initial gate evidence and delivery/blocker status, even offline. Detailed preflight blockers appear in `job.entry.readiness`; fresh post-delivery checks appear in `job.entry.observation.evidence.reviewGate`. `astack service wake` requests a targeted reconciliation pass after checks change; no cron, scanner or check watch is installed. Never resend pending/acknowledged input or start a replacement for an uncertain worker.

Workers return the versioned review JSON proposal with exact IDs/target, findings, blockers, gate policy and check snapshots. A proposal, UI done and delivered input are not accepted completion. Remote report authentication, fixes, GitHub publication, and merging remain planned; after-handoff initiation requires the explicit controls below. Explicit run operations handle host report acceptance and cancellation.

## Durable run outcomes and controls

Use `astack run inspect <job-id> [--json]` to recover assignment, current report/control, worker status, latest responses/continuations and retained cleanup offline. Task outcome and worker liveness are separate; a completed result with a running/unknown worker still retains capacity. Never infer cleanup permission from an accepted report, cancellation request, idle pane or empty resource summary.

`astack run report <job-id> --key <stable-key> --file <JSON-path> [--json]` explicitly asks the same-host orchestrator to validate and accept a selected worker proposal. The file is the original versioned report or `{proposal, artifacts}` with bounded relative path/digest/size references. Supply exact saved IDs and commit evidence. A parsed report is not proof of origin or business correctness; never feed arbitrary terminal text into acceptance. The operation checks acknowledged prompt bytes, owned checkout/branch/full SHA, clean completed work, review target/base/gate provenance and artifact bytes. Accepted report retries with the same key return saved evidence; changed input conflicts. Reports never release resources automatically.

For a needs_decision report, use `run respond <job-id> --key <key> --decision <report-id> --text <response>` to save a response without sending input. Then explicitly use `run resume <job-id> --key <key> --response <response-id>`. Resume creates a durable continuation of the same verified worker, with fresh configuration/ownership/review gates and keyed input. It never starts a replacement agent or changes execution policy. Pending/unknown input is not replayable; do not invent a new key to bypass uncertainty. An acknowledged continuation allows a later report, not accepted task completion. Approval/question UI handling remains deliberate operator work.

`run cancel <job-id> --key <key> [--interrupt]` saves intent before optional keyed Escape to a verified owned worker. It blocks future claims and launch/input. Never-claimed/proved-stopped jobs become cancelled; running/unknown jobs remain cancel_requested until trusted shutdown evidence. Escape acknowledgement is not shutdown. Use a separate explicit key to request interrupt later after an intent-only request. Existing terminal outcomes remain preserved. Worktrees, branches, user changes and uncertain resources remain retained.

`run events [--project <id>] [--job <id>] [--after <event-id> | --consumer <id>] [--limit <1–100>] [--wait <0–20000>] [--json]` reads/waits on local SQLite events. It neither polls GitHub nor injects worker prompts, and works independently of the service/pane. Process the page before explicitly acknowledging its `nextCursor` with `run cursor ack <consumer> --expected <old-offset> --after <nextCursor>` using exactly the same project/job scope. `run cursor inspect <consumer>` reads a saved offset. Reading and disconnects never advance cursors; replay is expected, exactly-once processing is not promised. Stale CAS updates, rewinds and future offsets reject.

Report/decision mutations use the live owning service; read commands work offline against existing migrated state. Keep credentials out of reports, response text and artifacts. Event records contain IDs/state/references, never arbitrary transcripts or response text. Automatic report discovery, orchestrator wake-up, shutdown and remedial actions remain planned.

## Host-authorized input recovery

`runtime authorize-input-retry --attempt <id> --key <input-key> --digest <sha256> --generation <number> --not-submitted --writer-stopped [--codex-executable <approved-path>] [--json]` is an explicit trusted host attestation after independent proof of non-delivery. Stop the coordinator and all original input controllers/descendants first; the CLI takes the coordinator lock. Never supply these flags from a timeout, idle screen, PID absence, parser reproduction alone, or worker proposal. The flags do not verify their own truth.

The operation checks the active assignment, current accepted policy and owned ready worker. It atomically archives the exact pending input generation and authorizes future retry of the same key/digest without sending input. Restart/wake the coordinator for workflow delivery, or explicitly supply the same runtime input. New actions have a newer generation; repeat authorization of an older generation cannot clear a newer send, and old acknowledgements cannot settle it. No new worker, capacity release, shutdown or cleanup is authorized. Other uncertain actions stay blocked.

## Explicit report collection and shutdown reconciliation

`astack run collect-report <job-id> --key <report-key> --session-file /absolute/path/to/rollout.jsonl [--json]` collects a final JSON report from one explicitly selected local Codex session and sends it through normal coordinator acceptance. It requires a saved ready runtime binding, matching metadata and exact saved assignment text, and the latest typed final response after the latest user message. It never searches other sessions or scrapes terminal output. Malformed reports reject; request a corrected report from the same worker if needed. `run report --file` remains the provider-independent path. New manual reviews use prompt version 3 with an object snapshot and numeric finding-line example. Finding line numbers must be positive JSON integers, not strings; saved version 1/2 prompt bytes remain unchanged.

After independently establishing that the exact worker and all descendants, attempt services and original effect writers have stopped, close only its owned worker workspace and stop the coordinator. Run `astack run reconcile <job-id> --key <key> --attempt <attempt-id> --launch <launch-id> --revision <control-revision> --worker-stopped --services-stopped --writers-stopped [--herdr-executable /absolute/path] [--json]`. These flags record truthful host attestations, never facts inferred from idle/done, Escape, missing panes or PID absence alone. Do not close the primary project workspace or reuse reserved names.

The offline command holds coordinator ownership and freshly verifies absence on the same saved Herdr server. It rejects stale bindings/revisions, pending actions, unresolved continuations and unknown retained resources. One transaction records host evidence, releases only exact bound worker/runtime/Herdr holds and frees capacity on restart; accepted task outcomes remain intact. Repeating the exact request returns its saved evidence. `cleanup.state=reconciled` is not checkout deletion; `retainedResourceCount` shows remaining holds and `resourceCount` includes historical records. Use normal `worktree remove` separately when ownership and cleanliness permit. No force deletion or branch removal is authorized.

## Explicit implementation publication

After normal report acceptance, independently verify the project and stop/exclude all original writers and descendants. Stop the coordinator. The host must explicitly approve the exact repository/branches/full SHAs, actor, PR body and optional review request; worker proposals do not authorize writes.

`astack handoff finish --file /private/host/handoff.json --writers-stopped [--git-executable /trusted/bin/git] [--github-executable /trusted/bin/gh] [--json]` holds coordinator ownership and validates the saved completed report, original acknowledged assignment, clean exact owned checkout and fresh accepted artifacts. The bounded UTF-8 JSON request uses `handoffRequestSchema` documented in `docs/handoff.md`: schemaVersion/jobId/reportId/key, explicit pull-request publication, expectedRemoteHead, named passed host-attestation checks with nullable artifact references, nullable review gate/instructionPaths, and nullable replaces. Verification assertions must reflect checks actually inspected by the host; the command does not run them. Do not commit request files or put credentials in them.

The operation journals a separate host publication attempt, pushes only an absent or verified fast-forward exact branch with an expected-head lease, creates one matching PR, rechecks exact evidence and atomically saves acceptance plus any explicitly requested review. Set `review: null` to disable the request. A requested review has not launched: manual `review submit` still needs a dedicated owned checkout and fresh policy/PR/SHA/CI gates; after-handoff dispatch requires the separate project/executor controls below.

Use `handoff inspect <implementation-job-id> [--key <key>] [--json]` offline. Inspect record phase and both push/PR effects: `persisted` alone does not mean accepted. Prepared/abandoned/error outcomes return nonzero. Repeating exact accepted intent returns saved historical evidence. A new key cannot bypass an uncertain write.

`handoff reconcile <implementation-job-id> [--key <key>] --writers-stopped [--git-executable <path>] [--github-executable <path>] [--json]` only observes saved effects and can accept matching evidence; it sends no remote writes. Original writers/children must be stopped and remain excluded. Repeating finish may begin an unclaimed next stage, but pending/unknown claimed stages only reconcile, even after expiry. Absence or edited/ambiguous remote evidence does not permit retry. Correcting a known preflight rejection requires a new key with `replaces` naming the exact current prepared record; replacement rejects uncertain push or any claimed/confirmed/unknown PR. Preserve evidence and investigate blockers.

`handoff follow-ups --project <id> [--after <handoff-id>] [--limit <1–100>] [--json]` lists requested reviews without dispatch/consumption. Its nextCursor uses handoff IDs, not follow-up IDs. It is a listing rather than an arrival cursor; use `run events` and consumer acknowledgements for durable arrival processing. No GitHub polling is installed. Publication neither stops workers nor releases capacity or removes worktrees; use their separate authorized operations.

## Targeted CI observation

`astack service run --observe-ci` enables bounded CI observation without enabling a worker runtime. Default service startup leaves observation disabled. Enroll only existing authorized work with `astack ci watch --handoff <implementation-job-id> [--handoff-key <publication-key>] --key <ci-key> [--timeout-ms <ms>] [--json]` or `astack ci watch --review <review-job-id> --key <ci-key> [--timeout-ms <ms>] [--json]`. Select exactly one source. A handoff must be accepted and contain a requested follow-up review; `review: null` grants no enrollment. The target/gate come from saved source evidence, never arbitrary PR discovery.

`ci inspect <ci-id> [--json]` and `ci list --project <id> [--after <id>] [--limit <1–100>] [--json]` read saved state offline. Inspect request phase/revision/reason, exact SHA, historical snapshot/error, next refresh and deadline. Ready is an observation-time result, not current dispatch authority. The list cursor is not a durable arrival cursor; use run events and explicit consumer acknowledgements.

`ci suspend|cancel|complete|resume <ci-id> --revision <current-revision> [--json]` controls only CI tracking. Resume alone accepts `--timeout-ms` to establish a new deadline (default one hour, supported 1 second–7 days). Resume revalidates original source/policy/context and never follows a newer SHA. Cancelled/completed tracking cannot resume. Completing CI tracking does not complete the review, stop an agent or release resources. Stale revisions reject; inspect before retrying. `ci wake [--json]` only schedules an observer pass and preserves budgets and future due times; it rejects if observation is disabled.

Matching host/repository/PR/full SHA requests share observations while applying their own gate policy. Missing/pending checks keep waiting; failed/skipped/cancelled checks, changed target/base, missing authority, draft/closed PRs, incomplete evidence and deadlines block. Blocked/suspended requests require explicit resume. No-CI behavior requires the saved gate's `allowNoChecks: true` plus private `execution.review.allowNoChecks: true`. For manual submission use `review submit --allow-no-checks`. This permits only an entirely empty check set with no selected required names, never failing or missing selected checks. Existing override reasons retain separate trusted permission.

The observer reserves a conservative per-host API allowance before bounded reads and persists schedules, exponential backoff with positive jitter, cooldowns and read claims. It sleeps until saved work is due and has no timer without active subscriptions. Restart respects unexpired claims, budgets and deadlines. Only expired reads can be repeated; this does not authorize replaying uncertain launch/input/push/publication writes. Historical successful snapshots can remain alongside a later error and do not pass a current gate by themselves. New/resumed revisions are not settled by older in-flight reads.

CI observation never creates a review checkout/job or launches a reviewer. Use `service wake` to reconsider an already authorized manual review with fresh target/readiness checks. After-handoff dispatch requires the explicit controls below. Enrollment/controls require the owning service, while source authority and API cwd come from the explicit registered target project, independent of caller cwd or Herdr focus.

## Explicit after-handoff review

`service run --observe-ci --after-handoff-review [--codex-herdr]` enables the follow-up executor; CI observation is required and the worker runtime is a separate opt-in. Project automation defaults to disabled. Inspect with `review automation inspect --project <id> [--json]`, then explicitly `review automation enable|disable --project <id> --revision <settings-revision> [--json]`. Settings live in trusted host state, not PR configuration.

After accepting a handoff containing a requested review, prepare a distinct clean owned reviewer checkout at its exact full SHA using the existing worktree operation. Attach it with `review follow-up enqueue --handoff <implementation-job-id> [--handoff-key <publication-key>] --checkout <reviewer-checkout-id> --branch <reviewer-branch> --commit <exact-head-sha> [--timeout-ms <1-second-to-7-days>] [--json]`. There is one immutable plan per authorized follow-up. No arbitrary PR target, implicit checkout creation, fetching or service provisioning occurs. Enqueue while disabled records a suspended plan without a watcher.

Use `review follow-up inspect <plan-id> [--json]` or `review follow-up list --project <id> [--after <id>] [--limit <1–100>] [--json]` offline. `waiting` means CI/admission work remains; `queued` is not a worker start; `dispatched` means a capacity/launch claim, not completion. `satisfied` references a compatible existing review without transferring ownership. Inspect the linked run separately for task, worker and cleanup outcomes.

`review follow-up suspend|resume|cancel <plan-id> --revision <plan-revision> [--json]` uses exact saved revisions. Disable suspends eligible plans and their owned CI waits; enabling never resumes them. Starting the service without its executor also suspends eligible backlog; restoring the flag requires explicit plan resume. Resume validates the unchanged binding/policy, uses the current enabled project revision and creates a fresh owned CI generation. It never resets an uncertain launch/input or selects a newer SHA. Claimed/dispatched/satisfied/cancelled plans reject these controls; use explicit run decisions/cancellation/reconciliation for claimed work.

Once owned CI is ready, the dispatcher rechecks source/policy/ownership and fresh PR readiness, atomically links review queue intent to the plan, and lets the existing coordinator enforce fresh readiness and capacity. Settings are rechecked in the claim transaction and at native launch/initial-input reservation boundaries. Effects already authorized before disable may finish; preserve blocked/unknown claimed attempts and resources. Already delivered reviews continue unless explicitly cancelled. Never infer shutdown or retry permission from the automation switch.

Manual `review submit` remains independent, uses its own request key and dedicated checkout, and does not create an automatic plan/watcher. Automatic assignments use prompt version 4 with plan provenance; old manual prompt bytes remain unchanged. Reviewers stay read-only and return structured findings. Findings publication, automatic fixes, approval/merge, provisioning and cleanup remain separate operations.

## Accepted review findings and linked fixes

- `review result inspect <job-id> --report-key <key> --json` reads accepted reviewed findings/artifacts, the last historical freshness observation and a `fixReference` offline. It makes no provider calls.
- With the coordinator stopped, `review result observe --job <id> --report-key <key> --json` refreshes exact PR/head/base evidence. Saved `current` is historical; stale/unavailable observations do not grant readiness.
- Normal `run report` rejects a moved review scope. Use `run report <job-id> --key <key> --file <proposal.json> --accept-historical-review --json` only when the host explicitly wants to retain reviewed findings as historical evidence. This does not bypass identity, acknowledged input, local SHA, artifacts or provider availability.
- Host-only publication requires coordinator exclusion and stopped original writers/descendants: `review result publish --file <request.json> --writers-stopped --json`. Request fields: schemaVersion 1, jobId, reportKey, exact reportId, stable key, actor, optional kind (`review` or `comment`), event (`COMMENT` or `REQUEST_CHANGES`) and zero-based findingIndexes. Omit indexes for all findings. Inspect and check text for sensitive data before publishing. Approval/merge are unsupported; oversized bodies reject without truncation.
- `review result publication <job-id> --report-key <key> --key <publication-key> --json` reads the saved effect. Confirmed retries use saved receipts without provider access; they can settle a previously missing local terminal host result. Claimed/unknown writes never resend or accept a bypass key. `review result reconcile --job <id> --report-key <key> --key <publication-key> --writers-stopped --json` performs read-only exact receipt lookup, including after the head moves. One publication intent per report is currently supported, with no replacement command.
- For an explicit fix, copy `fixReference` from inspection, add nonempty unique `findingIndexes`, and save the reference JSON. Prepare a fresh owned implementation checkout at its exact reviewed commit. Use ordinary `implement submit ... --task <concrete finding details> --fix-of <reference.json> --json`. The service validates source job/attempt/report/digest/SHA and links the new job transactionally. Never reuse the reviewer checkout or resume it as an implementer. A fix begins an ordinary new implementation/report/publication/review cycle; no automatic fix loop exists.

See `docs/review-results.md` and ADR 0019 for publication limits, cancellation, uncertainty and historical-result semantics. These commands do not close workers or clean up resources.

## Publication-attempt settlement

Successful handoff and review publication resolve their own host publication attempts, separately from worker completion/shutdown. If an older confirmed publication keeps checkout cleanup blocked, stop/exclude the coordinator and original writers and use the same `handoff reconcile ... --writers-stopped` or `review result reconcile ... --writers-stopped` key. Saved confirmed evidence can settle its missing terminal result without provider calls, pushes or POSTs. The first settlement appends `publication_finalized`; later repeats do not change result/event identity. Inspection/startup do not repair records. Pending/unknown effects remain unresolved. Never edit SQLite or change send keys to clear a cleanup hold. Verify worker shutdown and reconcile its separate resources before normal `worktree remove`; resources on jobs accepted after worktree preparation still block removal.

## Durable cleanup and retention

Use `cleanup request <job-id> --key <stable-key> --not-before <unix-ms> [--automatic] [--allow-unpublished] --json` after a terminal run on a dedicated ready owned checkout. Default retention also requires confirmed publication. Request and control commands work offline under coordinator ownership or through the running service. `cleanup inspect <job-id> --json` reads the frozen assignment, retention, phase, reason and revision without provider calls. One immutable request per run prevents bypass keys. No historical runs are enrolled automatically.

With the service stopped, `cleanup execute <job-id> --revision <cleanup-revision> --json` performs fresh checks and ordinary owned worktree removal. Worker resources must already be shutdown-reconciled. Alternatively supply all of `--attempt <id> --launch <id> --run-revision <n> --shutdown-key <key> --worker-stopped --services-stopped --writers-stopped` together, after obtaining independent host shutdown evidence. The flags are attestations, not requests to stop processes. Never derive them from idle/done, age, Escape or missing PIDs. Cleanup never kills workers/services, closes Herdr layouts or releases unknown holds.

Automatic removal requires both the saved `--automatic` request and `service run --cleanup`. It waits for retention and verified shutdown, using local wakes and retention timers without GitHub polling. Service startup without the flag suspends eligible backlog, and automatic requests received while disabled are saved suspended. Restoring the flag does not resume them. `cleanup suspend|resume|cancel <job-id> --revision <cleanup-revision> --json` controls unstarted plans; suspend retains resources indefinitely. Requests/deadlines cannot be replaced with a new key. Use a new dedicated checkout for another delegated task.

A persisted `blocked` plan preserves its checkout and states the blocker. `started` after interruption means uncertain cleanup, not successful removal: never retry it automatically. Stop/exclude the original cleanup writer and its children, then use offline `cleanup reconcile <job-id> --revision <started-revision> --writers-stopped --json`. It inspects/reconciles the exact owned worktree operation without replaying Git removal. It either verifies absence and completes, or restores a request for a separately authorized execution. Dirty/untracked/ignored/unowned resources remain preserved. Branches, primary spaces, marker containers, historical reports and registrations remain. Review can proceed while cleanup is blocked. See `docs/cleanup.md` and ADR 0020.

For a task cancelled before any worker launch claim, `run cancel` now closes its exact unclaimed initial launch and resolves the cancelled attempt locally, keeping `entry.claim` null. A local effect-resolution claim does not indicate a worker started. If an older never-launched cancellation blocks cleanup with `resource_in_use`, repeat the original `run cancel <job-id> --key <same-key>` with the service running. The first eligible settlement appends one cancellation event; reads/startup never heal it. Claimed, unknown or additional effects do not qualify and never become shutdown evidence.
